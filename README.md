# Explore With Me — микросервисная архитектура
Дипломный проект **Яндекс Практикума**. Изначально монолитное приложение по управлению событиями (ExploreWithMe) разделено 
на независимые микросервисы, взаимодействующие через Eureka + OpenFeign, с единой точкой входа через API Gateway.

## Архитектура

Проект построен по принципу **микросервисной архитектуры** с выделением доменных сервисов по бизнес-ответственности. Каждый сервис владеет собственными данными и предоставляет API для взаимодействия.

---

### Инфраструктурный слой

- **Discovery Server (Eureka)** — сервис-реестр, в котором регистрируются все приложения. Обеспечивает обнаружение сервисов без жёсткой привязки к IP-адресам и портам.
- **Config Server** — централизованный источник конфигурации для всех сервисов.
- **Gateway Server (Spring Cloud Gateway)** — единая точка входа для внешних клиентов. Все запросы от пользователей и Postman-тестов поступают только сюда (порт `8080`) и маршрутизируются в соответствующие микросервисы по пути запроса.

---

### Бизнес-слой (доменные сервисы)

- **User Service** — управление пользователями (регистрация, получение, поиск). Хранит данные о пользователях.
- **Event Service** — управление событиями, категориями и подборками. Основной сервис приложения.
- **Request Service** — управление заявками на участие в событиях. Обрабатывает создание, подтверждение и отклонение заявок.
- **Comment Service** — управление комментариями к событиям. Дополнительная функциональность группового проекта.
- **Stats Service** — сбор и выдача статистики просмотров событий.

---

### Принципы взаимодействия

1. **Внешние запросы** → Gateway (порт `8080`) → маршрутизация в нужный сервис.
2. **Внутренние вызовы** между сервисами → напрямую через **FeignClient** с разрешением адресов через Eureka (Service Discovery).
3. **Базы данных** → у каждого сервиса своя, общих таблиц нет.

## Сервисы и их ответственность

| Сервис | Ответственность | Порт |
|--------|-----------------|------|
| **discovery-server** | Реестр сервисов (Eureka Server) | `8761` |
| **config-server** | Централизованная раздача конфигурации | случайный |
| **gateway-server** | Единая точка входа, маршрутизация запросов | `8080` |
| **stats-server** | Сбор и выдача статистики посещений | `9090` |
| **user-service** | Администрирование пользователей | случайный |
| **event-service** | Мероприятия, категории, подборки | случайный |
| **request-service** | Заявки на участие в мероприятиях | случайный |
| **comment-service** | Комментарии к мероприятиям | случайный |

> Сервисы со случайным портом (`server.port: 0`) самостоятельно выбирают свободный порт при старте и регистрируются в 
> Eureka под этим портом. Для внешнего клиента конкретный порт не важен — все запросы проходят через Gateway.

## Базы данных

Каждый сервис владеет **собственной базой данных**. Разделение данных позволяет деплоить и масштабировать сервисы независимо.

| Сервис | База данных | Основные таблицы                       |
|--------|-------------|----------------------------------------|
| **user-service** | `user_db` | `users`                                |
| **event-service** | `event_db` | `categories`, `events`, `compilations` |
| **request-service** | `request_db` | `requests`                             |
| **comment-service** | `comment_db` | `comments`                             |
| **stats-server** | `stats_db` | `hits`                                 |

> Схемы создаются автоматически при старте каждого сервиса (`spring.sql.init.mode: always`). Ручных шагов по инициализации БД не требуется.

## Взаимодействие между сервисами

### Внутренние эндпоинты (Feign)

Эти эндпоинты существуют **только для межсервисных вызовов** и не предназначены для внешних клиентов.

#### `user-service` → используется всеми остальными

| Метод | Путь | Назначение |
|-------|------|------------|
| `GET` | `/admin/users?ids={ids}&from=&size=` | Батч-получение данных о пользователях по списку id |

#### `event-service` → используется request-service и comment-service

| Метод | Путь | Назначение |
|-------|------|------------|
| `GET` | `/events/{eventId}/info` | Получение данных события для валидации заявок |
| `GET` | `/events/previews?ids={ids}` | Батч-получение превью событий |

#### `request-service` → используется event-service

| Метод | Путь | Назначение |
|-------|------|------------|
| `GET` | `/requests/confirmed?eventIds={ids}` | Батч-получение количества подтверждённых заявок |

> **Батчинг:** Все внутренние эндпоинты принимают список id, а не один id. Это позволяет избежать проблемы N+1 запросов при построении списков (например, страница из 20 событий требует ровно один запрос за всеми данными, а не 20).

## Внешний API

### Основной API (из спецификации)

Спецификации находятся в корне репозитория:

- **`ewm-main-service-spec.json`** — категории, события, подборки, пользователи (admin), заявки
- **`ewm-stats-service-spec.json`** — статистика (`/hit`, `/stats`)

Разбиение на микросервисы **не изменило внешний контракт** — клиенты взаимодействуют с системой так же, как с монолитом.

### Дополнительная функциональность: Комментарии

| Метод | Путь | Доступ |
|-------|------|--------|
| `GET` | `/comments` | Публичный — список опубликованных комментариев |
| `GET` | `/comments/{commentId}` | Публичный — комментарий по id |
| `GET` | `/users/{userId}/comments` | Приватный — свои комментарии |
| `GET` | `/users/{userId}/events/{eventId}/comments` | Приватный — свои комментарии к событию |
| `POST` | `/users/{userId}/events/{eventId}/comments` | Приватный — добавить комментарий |
| `PATCH` | `/users/{userId}/comments/{commentId}` | Приватный — редактировать |
| `DELETE` | `/users/{userId}/comments/{commentId}` | Приватный — удалить |
| `GET` | `/admin/comments` | Админ — все комментарии |
| `PATCH` | `/admin/comments/{commentId}` | Админ — изменить статус |
| `DELETE` | `/admin/comments/{commentId}` | Админ — удалить любой комментарий |
